# PeachyPet 主窗口重设计与皮肤 Spec

日期：2026-11-03。状态：方向已选定，可以开工。第一节到第三节写的是已经谈定的内容；还没答复的问题都放在「待定」。

这份文档说的「原型 D」，是用户选定的合并版可点击原型（「C 的布局 + B 的气质」）。界面长什么样，以它当前的默认状态为准。

## 一、问题：用户卡在哪

前两条是用户的原话。后两条是我看代码后提出的，用户没有这样说过，但回复「1」选了包含这两处改动的方案。

1. **窗口看着不舒服。** 用户说：「整体页面风格全变的更好看一些」。用户对最新版 Masko 的印象是：「感觉整体看上去很舒服」。
2. **想换一身，现在换不了。** 用户问：「是不是可以给我的 peachypet 加上一个可自定义皮肤的功能？」看过原型后又说：「原型默认颜色不要橙色，并且默认 masko 不要狐狸，我当前用的这个天使挺好」。
3. **想知道发生了什么，要翻三个页面。** Activity、Notifications、Approvals 展示的是同一批事的不同切面：发生了什么、提醒了什么、要你处理什么。
4. **想知道代理接好了没、会话跑在哪，答案藏着。** 接入状态在设置和连接诊断里，主窗口看不到某个会话来自哪个代理、点了会跳到哪个应用。

各页面的实际使用频率没有统计数据，无法量化。

## 二、应该发生什么

每条末尾的标记表示验证入口，定义见第六节：【单测】【打包】【真机】。

### 外观与皮肤

- **S1** 窗口整体符合原型 D：三栏结构（导航、列表、详情）、剪纸色带、大字标题、侧栏常驻桌宠。→【真机】同窗口尺寸与原型 D 逐页对比截图，五个入口都没有结构差异才算过。
- **S2** 内置皮肤有奶油、蜜桃、晚霞、夜，另有自定义。切换后整个主窗口立刻变色，不用重启，也没有留在旧皮肤颜色的区域。→【真机】每个入口、每套皮肤各截一张图，逐张看。
- **S3** 外观页和标题栏都能换肤。外观页的预览卡显示各皮肤自己的颜色，不受当前皮肤影响，整张卡都能点。→【真机】在一套皮肤下点另一张卡的四个角和中心。
- **S4** 自定义皮肤用取色器选一个主色，其余颜色自动推导，界面实时预览。→【真机】拖动取色器，松手前窗口已变色。
- **S5** 换的皮肤和自定义的主色，退出重开后还在。→【真机】重启应用后比对。
- **S6** 所有内置皮肤的正文对比度不低于 4.5:1。自定义皮肤无论选什么主色都不低于这个值。→【单测】遍历内置皮肤；自定义皮肤取一组主色样本，至少包含纯白、纯黑、高饱和黄。
- **S7** 「夜」皮肤下主窗口真的是深色，不被强制成浅色。→【真机】截图确认。
- **S8** 皮肤系统做完、窗口结构还没重排时，选蜜桃后，除字体外，主窗口各页面与改造前相同。→【真机】改造前后同页面截图并排对比。

### 默认值

- **S9** 这台机器升级后，当前桌宠仍是 PeachMilky，不被重置。→【真机】升级前后对比。
- **S10** PeachMilky 这种只有视频、没有缩略图的桌宠，在侧栏、空状态和桌宠页都显示出角色形象，不出现空白或占位图。→【真机】三处截图。
- **S11** 默认皮肤是奶油：主色香槟金，主按钮、选中项、未读点和色带都不是橙色，与原型 D 的默认状态一致。新安装的用户和已安装的用户都是这样：已安装的用户升级后，没手动选过皮肤的也变成奶油。→【真机】清掉皮肤选择后启动一次，与原型 D 对比；【单测】没有保存过皮肤时取到奶油。

### 收件箱

- **S12** 导航只有五个入口：收件箱、会话、代理、桌宠、设置。→【真机】
- **S13** 收件箱上半是待处理（权限请求、提问、等待输入），下半是按时间倒序的历史。待处理为空时显示桌宠空状态。→【真机】触发一个真实权限请求，看它进入和离开待处理。
- **S14** 待处理为空时，在 1280×800 的窗口里，一屏至少能看到 8 条历史（原型 D 实测 8 条）。→【真机】数一屏里的条数。
- **S15** 旧 Notifications 和 Approvals 里的记录，升级后都能在收件箱找到，条数不少。旧 Activity 的逐条事件（最多 1000 条）也进入收件箱历史。→【单测】用旧格式数据加载后比对条数；【真机】抽查最早的一条。
- **S16** 历史可以按项目和代理筛选。升级前的旧通知没有代理信息，只能按项目筛选，也不会因此从列表里消失。→【单测】新旧两种记录混合时筛选。
- **S17** 未读有标记。键盘 ↑↓ 切换条目，U 标记已读。→【真机】

### 会话

- **S18** 活跃会话在上，最近结束的在下。每行显示引擎图标、项目名、标题、状态、宿主图标、最近活动时间。→【真机】与持久化的会话数据对照 5 条。
- **S19** 选中会话后，详情里能看到「从哪个引擎来、会跳到哪个应用」，下面是对应的跳转按钮。按钮跳到的应用与路线图上画的一致。→【单测】复用现有跳转测试；【真机】终端、Codex 桌面版、Paseo 各点一次。
- **S20** 宿主是「其他」时，跳转按钮置灰并说明无法跳转，点击后什么都不发生。→【单测】

### 代理

- **S21** 按 Claude Code、Codex、Copilot CLI 分块，每块显示接入状态、会话数、宿主分布，并有连接诊断入口。→【真机】
- **S22** 接入状态反映 hook 是否真的装好，不是「收到过事件」。在设置里关掉某个集成后，这里显示未安装。→【真机】关掉再打开一次；过程结束后配置恢复原样。
- **S23** 会话数和宿主分布的数字与持久化的会话数据一致。→【单测】固定数据算分布；【真机】与当前数据核对一次。

### 桌宠与设置

- **S24** 桌宠页显示全部已安装角色，当前角色有高亮，有创作新角色的入口，换桌宠后侧栏立刻跟着变。→【真机】
- **S25** 设置分通用、快捷键、通知、外观。现有设置项一个都不少，改动都能生效。→【真机】改版前列出全部设置项，改版后逐项勾对。
- **S26** 中英文切换后，新增的界面文字都有翻译，不显示翻译键名。→【真机】切到英文走查五个入口。

### 桌宠浮层

- **S27** 桌宠浮层的权限卡、展开面板、会话切换器跟着当前皮肤换色。允许和拒绝在每套皮肤下都一眼能分清。→【真机】每套皮肤下真实触发一次权限请求并截图。

### 桌宠资源中心

- **S28** 桌宠页能浏览线上的桌宠清单，选一只后下载、校验、导入，导入后立刻能换上。校验不通过就不导入，并告诉用户原因。→【单测】校验值不符时拒绝导入；【真机】下载一只并换上。
- **S29** 新安装的用户首次启动时，默认桌宠是 PeachMilky，从线上下载。下载完成前，桌宠位置显示它的静态图；下载失败时可以重试，应用照常可用。→【真机】在一个干净的用户账户里首次启动，分别在联网和断网下各试一次。
- **S30** 上传一只新桌宠只需两步：在应用里导出，再用一条命令发布。发布后，桌宠页的清单里能看到它。→【真机】发布一只测试桌宠，然后在桌宠页找到它。

## 三、绝对不能发生什么

前五条做错了撤不回来，或者后果难以补救。

- **N1 升级把历史清空。** 现在读取失败会按空列表处理，下一次保存就会覆盖旧文件。所以新增字段只要让旧通知解析失败，通知历史就没了。会话、审批记录和桌宠数据同样不能丢。→【单测】旧格式数据加载；【真机】升级前备份数据目录，升级后比对条数。
- **N2 权限答错。** 不能自动替用户回答请求、把回答发给错误的会话、丢掉请求，也不能让一个请求被答两次。换肤后，允许和拒绝在任何皮肤下都不能混淆。权限一旦放行，代理的操作可能已经执行。→【单测】复用现有权限测试；【真机】放行、拒绝各真实走一次。
- **N3 显示状态时改了用户配置。** 打开代理页、查看接入状态都只能读取。除非用户自己操作开关，不能写 Claude Code、Codex 或 Copilot 的配置，也不能把用户关掉的集成重新装回去。对比界面时同样不运行 Masko 客户端，它启动会改写这些配置。→【单测】读取前后配置内容不变；【真机】走查前后比对配置文件。
- **N4 安装时丢掉系统授权。** 只能用正式打包脚本安装，不能用临时签名或裸二进制覆盖，否则辅助功能和通知授权都会失效，用户只能手动重新授权。→【打包】脚本自带签名校验，安装后再核对一次团队标识。
- **N5 把 Masko 的专有素材带进仓库或安装包。** 只借鉴风格，图片素材一律不用。→【打包】列出安装包内的全部图片，逐一确认来源。
- **N6 Paseo 记录里的授权信息露出来。** 这些记录带 MCP 的 Authorization 头。代理页、详情页、诊断页和日志都只能用 ID 类字段。→【真机】查看诊断页和日志，搜索 Authorization 应无结果。
- **N7 通知洪峰下应用再次卡死。** 收件箱合并和换肤不能让这个问题回来。修复后的基线是 CPU 约 1%–8%，修复前是 95%。→【真机】重放一轮通知洪峰，同时看 CPU 和窗口响应。
- **N8 皮肤设置损坏导致应用打不开。** 保存的皮肤读不出来时，应用仍要正常启动，并用默认皮肤。→【单测】
- **N9 活动事件淹没通知。** Activity 事件并入历史后，用户仍能一眼找到通知和审批，S14 的一屏条数不因此下降。→【真机】在事件多的一天数一屏里的通知条数。

## 五、这次不做什么

- 不照搬 upstream 的六个入口。Everyday 小工具、Ask 问答、协作流程方向已定要做（O7），按 O9 之后单独出 spec。账号、商城、Studio 不做。
- 不改桌宠本身的动画和播放行为。
- 不改创作中心的功能，桌宠页只放一个入口。
- 不替换或下架内置的 7 只角色。它们的视频托管在 Masko 的服务器上，与 N5 冲突，是已知问题，这次不处理。
- 不给升级前的旧通知补代理信息。
- 不做皮肤的导入、导出、分享，也不做按时间自动切换。「日、夕、夜」只是皮肤的样子。
- 不处理这两件遗留事项：Paseo 压缩通知的那一对重复（103 条里 1 对）、后台记忆任务过滤的线上验证。
- 不为这次改动搭 UI 自动化框架。

## 六、从哪儿验

只用三个入口，从上到下。

| 标记 | 入口 | 负责什么 |
|---|---|---|
| 【真机】 | 用正式安装包装好的应用，按第二节逐条走查，并与原型 D 对比截图。真实触发一次 Claude Code 权限请求，再点一次 Codex 和 Paseo 会话的跳转 | 位置最高，界面和端到端行为都看它。仓库目前没有 UI 自动化测试，界面类条目只有这个入口 |
| 【打包】 | 现有的正式打包脚本（自带签名校验）和安装包资源核对脚本 | 签名、字体等资源是否进包、安装包内容 |
| 【单测】 | 现有的 `swift test`（当前 304 个用例全部通过，测试运行时与真实用户数据隔离） | 真机不好穷举或不能冒险的部分：旧数据升级、对比度、权限和配置安全。新用例都加在这里，不开新入口 |
